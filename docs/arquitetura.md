# Arquitetura

O navegador acessa uma API na mesma máquina. `ThreadingHTTPServer` escuta somente IPv4 loopback. Host deve ser exatamente o endereço informado, Origin só pode ser a própria origem e POST exige token CSRF de processo. Não há CORS, telemetria, CDN, uploads ou recursos externos. CSP impede scripts inline, enquadramento e avaliação dinâmica. Dados de arquivos são exibidos por `textContent`, nunca HTML.

`Engine` não depende da interface. Raízes são absolutas, físicas, canônicas, sem sobreposição com referências ou DATA_DIR; identidades de raízes também são registradas e verificadas. Links e tipos especiais são bloqueados. No POSIX, enumeração/hash abrem ancestrais por descritor e `O_NOFOLLOW`, e hash verifica identidade antes/depois. Um arquivo que muda durante leitura perde a confirmação. Não se garante snapshot consistente de uma pasta viva; inventário é uma observação revisável, não autorização para movimentação.

Varredura em thread separada, streaming de 1 MiB, concorrência de hash fixa em **1** nesta versão. É uma limitação deliberada; ajuste de concorrência é uma extensão futura, não uma opção já implementada. A lista de metadados fica em memória e SQLite; a interface usa paginação de 50 itens. Isto limita DOM, não memória de todos os metadados. Muitos milhões de arquivos precisariam paginação no banco e inventário incremental. Progresso persiste entre etapas; cancelamento não reutiliza hashes incompletos. Retomar faz nova varredura com invalidação por identidade/tamanho/mtime/ctime/nlink.

Inventário compara **origens contra referências**, nunca usa outra origem como única cópia preservada. Assim um lote de origens idênticas preserva pelo menos uma referência externa ao conjunto. Grupos são derivados de SHA-256 com IDs por época de configuração. Metadados e fluxos alternativos não entram na prova. Todas as referências de um item ficam consultáveis no cartão.

Um plano contém snapshots imutáveis, configuração, IDs, bytes, referência preservada e decisão excepcional por item. Revisão relê os hashes completos; execução repete a leitura sem cache. O adaptador deve revalidar ambos os itens imediatamente antes da operação nativa. A política atual aceita a janela após liberar os handles; não se promete atomicidade. Ativação depende de prova de reciclagem nativa, ainda pendente no Windows.

SQLite WAL, `synchronous=FULL`, guarda o plano e a operação antes de atuar. Cada item ganha intenção antes de chamar o adaptador. Repetir um ID retorna o resultado anterior. Depois de reinício, intenções sem resultado se tornam incertas, com bloqueio de novos planos para a mesma identidade/localização. Ausência do caminho sem evidência nativa não vira sucesso. Um usuário local capaz de ler os dados ou executar código na conta já tem acesso aos arquivos; isto não é isolamento contra processos maliciosos da própria conta.

Distribuição local por checkout ou ZIP gerado por `python3 tools/build_local.py`. Não há instalador nem pacote publicado. `Abrir Tidyup.cmd/.pyw` inicia `desktop.py`: serviço em porta loopback dinâmica, navegador padrão e reabertura via identificador de instância em DATA_DIR. `Tidyup.html` é autocontido e, via file://, não solicita API nem habilita acesso ao disco. Não há protocolo customizado/registro instalado. Adaptador e testes podem ser consumidos independentemente no futuro.

Windows tem leitura experimental por handles, não validada neste ambiente. `windows.py` abre ancestrais sem compartilhamento DELETE, evita seguir reparse e abre arquivo sem compartilhar WRITE/DELETE. Isso protege leitura; o mesmo bloqueio impede reciclagem por Shell. COM de diagnóstico só configura flags e não enfileira operações. Lixeira continua indisponível em produção.
